# ADR-001: 论文详情使用 Hash 路由和只读按键查询

## Status

Accepted

## Date

2026-07-22

## Context

PaperHot 是由本地 Node 服务托管的单页前端，现有页面导航使用 hash。论文详情需要满足以下约束：

- DOI 和 URL 可能包含 `/`、`?`、`#` 等路由保留字符。
- 详情地址必须支持直接刷新和浏览器前进/后退。
- 直接刷新时前端论文数组可能尚未加载。
- 归档是较完整的论文来源，但用户可能保留仅存在于收藏快照中的论文。
- 查看详情不能隐式修改论文库、收藏或操作日志。
- 收藏、已读、标星、短标题等状态已有独立 API，不应为详情页复制一套状态。

## Decision

1. 论文详情地址使用 `#paper/<encoded-stable-key>`，整个稳定键通过 `encodeURIComponent` 编码为一个不透明路由段。
2. 前端使用统一解析入口返回 `{ page, key }`；应用启动、hash 变化，以及可能覆盖详情的通用异步刷新从当前完整路由恢复页面。页面专用回调只有在当前 page 匹配时才单独重绘。
3. 新增只读 `GET /api/papers/by-key?key=...`：先查归档，未命中时回退收藏快照，仍未命中返回 404。
4. 详情请求用请求编号和当前路由键双重校验，避免迟到响应覆盖其他论文或列表页。
5. 详情页复用现有收藏和 notes 状态接口，不新增持久化文件，不改变备份格式。

## Alternatives Considered

### 只依赖前端列表缓存

- 优点：不需要新增服务端接口。
- 缺点：直接刷新时缓存为空；仅收藏快照中的论文也可能不在当前列表。
- 结论：不能满足可分享和可刷新恢复的详情地址。

### 把完整论文对象写入 URL 或 localStorage

- 优点：刷新时可以在浏览器侧恢复部分内容。
- 缺点：URL 过长且会泄露内容；localStorage 快照会与归档漂移，也绕开现有本地数据和备份边界。
- 结论：拒绝复制论文数据，URL 只保存定位键。

### 为详情页创建独立数据文件和状态 API

- 优点：可以针对详情页单独建模。
- 缺点：会复制归档、收藏和阅读状态，产生双写与一致性问题。
- 结论：详情页是现有论文和阅读状态的视图，不是新的数据所有者。

### 改用服务端路径路由

- 优点：URL 形式更接近传统多页应用。
- 缺点：需要为任意深链接增加服务端 HTML fallback，并与当前 hash 导航并存或迁移；对本地单页应用没有足够收益。
- 结论：沿用现有 hash 架构，将参数解析补完整。

## Consequences

- 论文详情可以从列表进入，也可以通过地址直接恢复。
- 查看详情保持无副作用；数据和备份格式不变。
- 归档记录优先于收藏快照，避免旧快照遮蔽更新数据。
- 稳定键不是永久数据库主键：标题回退可能重名，未来若 ID 规则变化，需要持久化路由 ID 或旧键别名迁移。
- 可能覆盖详情的通用异步重渲染必须保留完整路由；页面专用回调必须先校验当前 page，新增相关流程时需要相应回归测试。
