paperHOT first-version approaches

All three keep the domain configurable. The difference is how much automation we build first.

A. Static Curation Board
paperHOT | Today | Tags | Sources
Manual JSON / Markdown items
Daily list page
Detail pages

A. Manual-first static site

Fastest to ship. You manually provide papers or links, and the app formats them into AIHOT-like cards.

B. Semi-automated paperHOT
Sources -> Ingest -> Score -> Review -> Publish
arXiv / bioRxiv / HF Papers
RSS / GitHub / blogs
LLM summary + tags
Daily HOT page

B. Semi-automated mixed-source system

Recommended. Fetches mixed sources, scores candidates, drafts summaries, then keeps a human review step.

C. Fully automated pipeline
Scheduler | Crawlers | DB | LLM | Web | Admin
Collectors
Dedup DB
Ranking
LLM jobs
Review UI
Deploy

C. Full production automation

Most complete, but likely too much for the first cut: scheduler, database, auth, admin UI, retries, and deployment.

Recommendation

  • Start with B so the output feels real quickly.
  • Keep source and domain rules as config.
  • Use review files instead of a heavy admin backend first.

Avoid in v1

  • Login system and full admin dashboard.
  • One-off crawler complexity for every source.
  • Hardcoding microscopy-specific ranking logic.
